# Skill Manager v0.3.1

Use the bundled `scripts/manager.py` (Python 3.9+). All paths are relative to this skill's folder unless absolute. Do not claim a command ran without actual tool output. Never execute scripts contained in imported skills during import or self-test.

## Setup (first use)
1. Determine whether the Agent has access to the user's real local filesystem and shell. A cloud sandbox is not the user's computer. If remote-only, offer the cloud workflow below.
2. Default to local-only setup. Scan first with `python3 scripts/manager.py setup`. Show a concise inventory and ask once for approval to consolidate existing safe global skills locally and configure the device-level scheduler. Do not bundle remote upload into local approval.
3. Once approved, run `python3 scripts/manager.py setup --approve-import --schedule` (omit schedule if not approved). Register verified adapter/project directories as needed. Initialization runs isolated self-tests. Then ask exactly once: "Do you need to use these skills across computers?" If no, no answer, or no storage configuration supplied, finish local setup without further prompts. If yes, suggest a dedicated private GitHub repository or an existing synced cloud folder. Configure only a provided, authorized destination. A GitHub repository may be created using authenticated official tooling if explicitly approved and supported; never use the public SkillHub source repo. Cloud-folder transport is not implemented yet; do not promise it. Existing populated local libraries require safe migration before Git connection; report this limitation rather than overwriting. Never ask for credentials in chat.
4. Explain that shared directory readers discover the same files; symlinks require platform support and may require Agent refresh. Backups are retained outside active roots when original files are replaced by links. Do not delete backups automatically.

## Install a Skill
For every install request handled by the Agent, invoke this manager first. Check `list` and inspect existing record by name and source/content, then obtain the actual skill package using trusted tooling into a temporary local directory. Inspect its instructions, scripts, dependencies, licensing and sensitive content. Get explicit approval before importing/uploading. Run `python3 scripts/manager.py install <path-to-skill-folder> --approved`. It logs precheck and postcheck, does not overwrite conflicting names, and syncs if configured. If the folder is for a project, do not install it as global; keep it under the project and inventory it with `setup --project ...`. Verify that the Agent actually discovers and can use the skill. Do not treat a pending/conflict result as installed. Native UI installs and third-party CLIs may bypass this Skill; no universal hook exists. Periodic scanning is a fallback, not proof of pre-install interception.

## Manage
- `python3 scripts/manager.py list`: list records and configured directories. Timestamps are first-seen, not original creation dates. Usage counts are unknown.
- `python3 scripts/manager.py sync`: pull, detect unapproved local folders, expose active skills, push. `--approve-import` imports all scanned eligible folders; only use after reviewing and getting approval. It may also adopt matching physical folders into links, preserving backups.
- `python3 scripts/manager.py disable NAME` / `delete NAME` / `restore NAME`: explicitly authorized actions; logical deletion retains contents and tombstone. Unmanaged original copies are not deleted.
- `python3 scripts/manager.py test`: isolated self-tests. Report actual pass/fail and unverified real environments. For actual environment verification, inspect configured paths, Git status, scheduler logs, and ask each Agent to invoke a harmless test skill using its native interface. A simulated test never counts as real Agent verification.
- To update a conflicting skill, review both versions and reconcile manually; automatic overwrite is intentionally disabled in V1.

## Cloud-only workflow
Do not run local setup in a cloud sandbox and claim it changes the user's machine. If an authorized connector permits reading the user's private GitHub repo, read `records/*.json` and active `skills/<name>/SKILL.md`, inspect dependencies and resources before using instructions. Dynamic reading is not native installation or automatic discovery. If connector access is unavailable, request a standard export/import package. Do not claim automatic management of the platform's installed skills unless a verified official interface actually supports it. Never call unauthorized private APIs or automate credentials.

## Output
Summarize discovered paths, actions, blockers, and verified results. Never upload confidential project content or credentials. Never imply all tools were connected when only file access was tested.

## Mandatory post-install catalog and management panel
After every installation attempt handled by the Manager (including duplicate, conflict or failed attempts), and when the user requests the directory, render the latest full catalog from the actual command output or `python3 scripts/manager.py catalog`. Never invent data or omit entries. The directory covers the managed library and configured roots, not inaccessible cloud accounts.

### Required compact layout
- Title: My Skills. No aggregate counts, KPI cards, charts, introductory narration, or separate provenance sections.
- Exactly two scope sections when nonempty: Global Skills and Project Skills (localized to the user's language). Identify the relevant project for project skills without adding unnecessary headings.
- Responsive dense grid: 3–4 columns on wide panels, 2 on ordinary panels, 1 on narrow panels. Each skill is an independent compact horizontal item: name | NEW (only if actually newly collected) | 自建 / Self-created (only if origin.kind is self) | visible trash icon. Place the self-created label immediately before the delete control. Use a subtle neutral background or no background, tight spacing, no heavy borders, no individual tall cards. Allow long names to wrap; do not truncate.
- Third-party, modified and unknown origin do not get a self-created label. Do not infer authorship. Preserve actual origin metadata for detail queries.
- Label inactive/unmanaged/conflicting entries inline when relevant. Deleted records belong in an optional recovery view, not the active grid; do not conceal them if the user requests deleted records.
- No visible disable switch. Retain disable and restore commands for explicit requests. Offer recovery only when applicable. End with at most one short line for sync mode or actual blockers.

### Independent delete action
Use a directly visible trash control for each individual skill only if the host supports a real action callback or an action that sends a new user turn to the Agent. No ellipsis menu. Each control must target the exact record and scope, including the project identity where applicable; never use a name alone to disambiguate conflicting records. On activation show a confirmation identifying the skill, scope and removal effect; cancellation changes nothing. For an unambiguous managed global record, after confirmation call the trusted local CLI `python3 scripts/manager.py delete NAME` using a validated name passed as a separate argument. The current CLI performs logical deletion, removing managed links and retaining recoverable contents and tombstones; it does not delete unmanaged originals or project-local files. For unmanaged, project-local, conflicting entries or the manager itself, show why direct deletion is unavailable, or use a separately verified, authorized platform-specific workflow; never dispatch them to the global delete command. Do not present unsupported controls as actionable. For hosts without real callbacks or local execution, use compact text entries with a natural-language delete instruction instead. Never fake deletion with client-side UI state or assume a cloud sandbox is the user's computer. After a real successful command, re-read catalog and verify state and link removal, then refresh the panel; if synchronization or deletion fails, report the failure and actual resulting state. Recovery uses `restore NAME` for an authorized managed global record, followed by verified refresh. Do not claim other devices have completed synchronization until verified.

For remote-only execution use authorized repository records and label limitations. Scheduled scans cannot force a visible message into an unrelated Agent conversation.

## Provenance and concise output
Use `install PATH --approved --origin self|third-party|modified|unknown --source-url URL` (source URL optional). For a newly created skill explicitly record self; for a verified external installation record third-party; for a confirmed derivative record modified and retain its original public source URL. Unknown historical authorship stays unknown even if a Git remote exists. Correct managed entries on user confirmation with `origin NAME KIND --source-url URL`. Never infer authorship from a folder name or an account name alone. Display only global/project groups using the compact grid above, with a self-created inline label and no aggregate summary data; do not narrate every command. Report only actual failures and next actions. .git metadata is excluded from new imports; credential scanning remains required. For persistence, with permission append a minimal non-duplicated rule to the Agent's documented global instruction file: before every skill installation invoke skill-manager to check duplicates, after installation synchronize and display catalog; on skill creation record origin self. Only claim enforced hooks where independently tested; scheduled scans detect bypasses but cannot enforce pre-install checks. Windows and macOS scheduled sync scans new files for review without unattended upload approval. Do not equate detection with automatic import.
